# Детали публичного контракта

Схемы полей и доступные операции — в [OpenAPI](../openapi.yaml).
Все запросы относятся к организации ключа. `application_id`, `installation_id`,
`subscription_id`, `message_id`, `delivery_id` — UUID; `device_id` и `external_user_id`
— строки вашей системы, до 255 символов.

## Приложения и окружения

Приложение относится к проекту и имеет платформу `ios`, `android` или `web`.
Установки и подписки разделены на `development` и `production`. Для отправки нужна
существующая запись окружения приложения. Приложения, окружения, API-ключи и credentials
провайдеров настраиваются через административные инструменты организации;
публичные операции их создания/списка/изменения в эту спецификацию не включены.

`POST /v1/messages` определяет окружение по активным подпискам всех получателей.
Все пары установки/подписки должны относиться к указанному приложению и одному
окружению. Отправка не принимает `environment`, `environment_id`, сырой токен,
`user_id`, `external_user_id` или сегмент вместо `recipients`.

При ключе с `environment_id` обработчики устройств проверяют тип окружения
`env_type`, а не совпадение приложения с записью окружения ключа. Отправка также
сравнивает тип окружения подписок; маршруты чтения сообщений/отправок проверяют
точный `environment_id`. Поэтому не считайте environment-scoped ключ механизмом
ограничения регистрации только одним приложением проекта. Для server Web Browser API
проверка окружения включает приложение. У удаления подписки через
`DELETE /v1/installations/{id}/subscriptions/{subscription_id}` есть проверки
организации/проекта/установки, но нет отдельной проверки `environment_id` ключа.

## Установки и токены

Повтор `POST /v1/installations` с теми же `application_id`, `environment`, `device_id`
обновляет `os_version`, `app_version`, `sdk_version`, `device_model`, время активности
и возвращает существующий ID с HTTP `201`. Пропущенные поля метаданных при повторе
становятся пустыми (`nil`); платформа существующей установки не меняется.

`POST .../tokens` принимает `apns`, `apns_voip`, `fcm`, `web_push`.
`huawei` и `rustore`, хотя встречаются в серверных enum, DTO регистрации не принимает.
Длина токена 32..1024, окружение обязательно и совпадает с установкой.
Для `web_push` token равен endpoint; передавайте `keys.p256dh` и `keys.auth` из браузера.
Server endpoint проверяет web-платформу; строгие криптографические проверки
endpoint/keys реализованы в [browser endpoint](web-browser.md).

Дедупликация токена действует внутри приложения, окружения и провайдера.
Повтор активирует подписку и очищает отметки инвалидности. Server API допускает
перенос такой подписки на другую установку; browser API запрещает перенос.
Ответ server регистрации: `subscription_id`, маскированный `token_prefix`, `status`;
browser регистрации токена: только `subscription_id`.

`login` привязывает установку к `external_user_id`, создавая внутреннего пользователя
при необходимости. `logout` снимает связь, сохраняя установку и токены. Это не вход
в аккаунт PushPilot и не удаление push-подписок. Legacy `PATCH` меняет только эту связь,
возвращает `{}` с HTTP `200`; новый код должен использовать login/logout.

## Отправка и payload

`POST /v1/messages` требует 1..10000 пар `installation_id`/`subscription_id` и JSON-тело
до 65536 байт. Лимит тела может быть достигнут значительно раньше 10000 получателей.
Дубликаты пар в массиве не устраняются — каждая создаёт отдельную отправку.
Подписка должна быть активной, принадлежать установке и приложению.

| provider | platform | notification_type | Провайдер подписки |
| :--- | :--- | :--- | :--- |
| `apns` | `ios` | `alert`, `background` | `apns` |
| `apns` | `ios` | `voip` | `apns_voip` |
| `fcm` | `android` | `alert`, `background`, `data` | `fcm` |
| `web_push` | `web` | `alert`, `background` | `web_push` |

Платформа приложения должна совпадать с запросом. Это проверяется при отправке;
регистрация установки не гарантирует совместимость всех provider/platform.

`payload` — JSON object формата PushPilot. Worker читает `title`/`body` (строки),
`badge` (целое), `sound` (строка), `custom_data`, `apns`, `android` (объекты).
HTTP-обработчик проверяет только наличие объекта: ошибки вложенных типов могут
возникать асинхронно после `202`. Произвольные неизвестные поля сохраняются,
но worker их не использует. `null` у известных полей допустим как отсутствие значения.
Для alert задайте непустой `title` или `body` (FCM иначе завершится ошибкой payload).

| Поле | Использование |
| :--- | :--- |
| `title`, `body` | Текст alert для APNs/FCM/Web Push |
| `custom_data` | Пользовательские данные; Web Push передаёт их как `data` |
| `badge`, `sound` | Дополнительные поля alert |
| `apns` | Дополнительные поля APNs верхнего уровня; ключ `aps` не подменяет генерируемый envelope |
| `android` | FCM: `image`, `sound`, `badge`, `channel_id`, `tag`, `color`, `click_action`, `priority`, `ttl`; для alert также `ttl_seconds` как fallback |

APNs формирует `aps` сам: alert содержит title/body, background — `content-available`;
VoIP использует custom_data и apns. Передавайте формат PushPilot, а не готовый
`aps` или FCM `message` envelope. `android.priority` — провайдерное `high`/`normal`,
отдельное от верхнеуровневого приоритета очереди.

FCM преобразует значения `custom_data` в строки, оставляет до 10 пар, исключает
пустые значения, недопустимые ключи и ключи с префиксами `gcm.`, `google.`, `from`.
Допустимые символы ключа — латинские буквы, цифры, `_`, `.`, `-`. При превышении
10 пар выбор ограниченного набора зависит от обхода Go map; передавайте до 10 пар.
Web Push alert передаёт title/body/badge/sound/data, background — пользовательские данные.

## TTL и повторные попытки

TTL очереди начинается при создании сообщения; минимум 60 секунд. Сервер обрезает
запрошенный TTL по классу приоритета и возвращает фактические `ttl_seconds`, `expires_at`.

| priority | Максимальный TTL, секунд | Максимум попыток worker |
| :--- | ---: | ---: |
| `critical_voip` | 600 | 5 |
| `transactional` | 7200 | 8 |
| `normal` | 86400 | 8 |
| `bulk` | 604800 | 5 |

Временные ошибки провайдера могут повторяться с задержкой до TTL/лимита попыток;
постоянные ошибки завершают отправку. В истории видны `attempt_count`, `max_attempts`,
`error_code`, `error_details`; это одна запись на отправку, не журнал попыток.
Точные задержки и доступность провайдера не являются гарантией времени доставки.

Очередной TTL не гарантирует одинаковый TTL у провайдера: APNs worker не передаёт
верхнеуровневый TTL в provider request, FCM берёт TTL из `payload.android` или свои
значения по умолчанию (alert — 86400, background/data — 604800 секунд).
Web Push получает оставшееся время до `expires_at`. Поэтому сообщение,
уже принятое провайдером, может оставаться у него после TTL очереди.

## Статусы сообщения

`POST /v1/messages` всегда возвращает `status: pending`, включая ответ из idempotency
кэша. Начальные записи отправок создаются со статусом `queued`. Для актуального
состояния читайте `GET /v1/messages/{messageID}`:

| Условие для deliveries | Агрегированный status |
| :--- | :--- |
| Нет отправок | `pending` |
| Все `delivered` | `delivered` |
| Все `sent`/`delivered` | `sent` |
| Есть `pending`/`queued`/`sending` | `processing` |
| Нет активных и есть `failed`/`expired` или другой неуспешный статус | `failed` |

`sent` фиксирует принятие провайдером. Публичного маршрута подтверждения receipt,
opened/clicked или автоматического превращения `sent` в `delivered` в этом роутере
нет. Поле `delivered_at` необязательно и требует отдельного подтверждения устройства.

## Idempotency

`idempotency_key` — необязательное поле JSON, до 255 символов; пустая строка отключает
кэш. Заголовок `Idempotency-Key` не читается. Область кэша: организация + ключ,
без добавления проекта/приложения/окружения. Используйте уникальный ключ логической
отправки с учётом всех этих измерений.

После успешного запроса результат доступен 24 часа от создания кэша. Повтор сначала
проходит обычную валидацию тела, приложения и текущих подписок: удалённый/инвалидный
получатель может привести к `404` вместо кэшированного результата. После этой проверки
сервер возвращает прежние ID, времена и TTL с `202`, не сравнивая тело с первоначальным.
Флага `cached` в публичном ответе нет; текущий статус читайте отдельно.

Не отправляйте параллельно одинаковый ключ: проверка кэша выполняется до транзакции;
гонка на уникальности может вернуть `500 enqueue_failed` одному из запросов.
Проверка истёкшего кэша не удаляет его, а новая вставка использует ту же уникальную
пару: повторное использование ключа после 24 часов может вернуть `500`, пока запись
не удалена. Используйте новый ключ для новой отправки независимо от возраста старого.
Гарантии exactly-once для обращения к внешнему провайдеру нет.

## История и пагинация

`limit` по умолчанию 50, ограничивается 1..200; `offset` по умолчанию 0,
отрицательное значение становится 0. Используются числовые значения, непарсируемые
строки оставляют default; в текущей реализации числовой префикс строки также может
быть принят. Фильтры `from`/`to` передаются в запрос к хранилищу без отдельной HTTP
валидации: используйте корректные RFC 3339 даты и UUID. Некорректные фильтры могут
вернуть `500`, а не `400`.

`GET /v1/messages`: `application_id`, `from`, `to`, `limit`, `offset`.
`GET /v1/deliveries`: те же параметры плюс `message_id`, `status`, `platform`.
`from` включительно, `to` исключительно; фильтрация по `created_at`.
`items` может быть `null` вместо пустого массива; обрабатывайте оба варианта.
Сортировка `created_at DESC`; отдельного стабильного tie-breaker нет.

`GET /v1/messages` возвращает записи Message, а не DTO статуса. `payload` имеет тип
Go `[]byte`, поэтому в HTTP JSON это base64-строка, которую надо декодировать в исходный
JSON. В ответе детализации сообщения вместо payload возвращаются агрегированный
status и deliveries. Поля timestamp с nil в Delivery опускаются.

## Аналитика

`GET /v1/analytics/deliveries` поддерживает только `application_id`, `from`, `to`.
Пагинации, фильтров status/platform и временного шага группировки нет.

- `items`: count записей отправок, сгруппированных по status/platform/application_id,
  в проекте ключа; при `environment_id` — в точном окружении ключа. Период по created_at.
- `usage`: для ключа без ограничения окружения — суммы счётчиков всей организации,
  включая другие проекты. Для ключа с environment_id — события usage, связанные
  с отправками его проекта/окружения. `application_id` на usage не влияет.
  `from`/`to` применяются к `period_start`, а не ко времени конкретной отправки.
- `quota`: JSON limits текущего плана организации. Фиксированная структура и значения
  в контракте не заявляются; при невозможности загрузить план/usage возвращается `500`.
- `sent_semantics`: `provider_accepted`; `delivered_evidence`: `device_confirmation_only`.

Это не отчёт о фактическом получении уведомлений устройствами. `items`/`usage` могут
быть `null`. Результат не обещает равенство суммы `items` и `usage`: их области и
правила учёта различаются.
